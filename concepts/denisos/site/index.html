Three problems worth solving.
Kept generic on purpose: the problem, the decision, the trade-off and what changed.
2024 — 2026 · TELECOM ACQUISITIONS
Making supplier onboarding
repeatable.
AZURE · SERVICE BUS · EVENT-DRIVEN · DOMAIN MODELLING · MENTORING
Problem
Every supplier had its own API, data formats, rules and failure modes. Each new one meant custom work spread across sales journeys and back-office systems.
Decision
A supplier-agnostic integration layer: one internal domain model, an adapter per supplier, and business events on a message bus instead of point-to-point calls. I designed it and owned it from domain modelling through deployment, monitoring and production support.
Trade-off
More design up front, and eventual consistency to handle between services, in exchange for a core that doesn't change every time a supplier does.
Result
Adding a supplier became repeatable work instead of a project, coupling between systems dropped, and high-volume sales stayed reliable and observable. I also mentored two developers on the team.
2023 — 2024 · RAYMOND JAMES
Upgrading a regulated platform
without the drama.
PHP 8 · MYSQL 8 · PHPUNIT · REGRESSION TESTING · INCREMENTAL MIGRATION
Problem
Business-critical wealth-management systems needed to move from PHP 7.4 to 8.2 and from MySQL 5 to 8. The code quietly relied on behaviour the new versions no longer tolerate: stricter SQL grouping, invalid dates, warnings that become errors.
Decision
Build a regression-test baseline first, then fix compatibility issues incrementally across applications and databases, instead of rewriting.
Trade-off
Time spent on tests before any visible progress, in exchange for releases everyone could trust.
Result
Migration and release risk went down without sacrificing stability for the people who depended on the platform.
2019 — 2021 · DEKO
Replacing a monolith without
stopping the business.
JAVA · DDD · EVENT STORMING · STRANGLER PATTERN · AWS SQS
Problem
A long-running lending platform had grown into a legacy monolith, and the lending operations it supported couldn't stop while it was replaced.
Decision
Domain-driven design and event storming to find the real business boundaries, then the Strangler Pattern: move one capability at a time into Java services, with Go and Python components, connected by asynchronous messaging on AWS SQS.
Trade-off
A slower, staged migration with old and new running side by side, instead of a big-bang rewrite and a risky cut-over.
Result
Business-critical lending kept running throughout, while capabilities moved to the new platform step by step.
The kind of platform I build
Five things I hold to
01
Design for failure.
Timeouts, retries, idempotency and outboxes go in on day one, not after the first incident. Partners will be slow. Queues will go down.
02
Make change safe.
A test baseline first, then small, reversible steps. I'd rather modernise around what already works than bet the business on a rewrite.
03
Model the business first.
Domain modelling and event storming before code. Getting the boundaries right saves more time than any clever implementation.
04
Own it in production.
Logging, tracing and alerts are part of the feature. If I built it, I want to know when it's unhappy, before a customer does.
05
Raise the team.
Mentoring, honest code reviews and writing decisions down, so knowledge doesn't live in one person's head.

      A word game became a systems problem
      How a simple letter-changing game turned into real-time multiplayer engineering.
      Word Duel started with a small idea: change one letter of a word, make another valid word, and keep going. TALK becomes WALK, then WALL. It doesn’t take much explaining. Building it so two people can compete fairly is a different problem.
      The browser isn’t the referee
      The interface uses Vite and vanilla JavaScript; the backend runs on Cloudflare Workers, with each game room held in its own Durable Object. The server decides whether a move is valid. The browser can display a countdown and let a player edit tiles, but it doesn’t get to decide whose turn it is or whether a late move should count.
      A room applies one action at a time, then pushes the new state to both players over WebSockets. That matters when players act at almost the same time, a deadline expires, or a request is retried.
      A word can’t just be valid
      It has to be the right length, change exactly the configured number of letters in place, and not have been used before. The shared set of used words persists across rounds and rematches. The rules are simple; reliably enforcing them is the interesting part.
      The computer plays the same game
      The bot occupies a player seat and plays through the same server-side engine. Difficulty changes think time and move strategy, not the rules of validation.
      All the little edges
      Turn deadlines are defined by the server, and each room sets an alarm for the next one. The same alarm closes idle connections and clears out old rooms. Match results are recorded with receipts so retries don’t create extra wins. Definitions come from a static WordNet-backed word dataset.
      The lesson wasn’t really about words. It was how quickly a tiny interaction becomes a problem of shared state, fairness and handling failure.

      The Conversations We’re Losing to AI
      Are we becoming more productive developers but less collaborative engineering teams?
      There’s been plenty of debate about whether AI will replace software developers. I’m more interested in a different question: what is AI doing to the way developers work with each other?
      I’ve been writing software for 17 years, and AI is one of the biggest changes I’ve seen. I use it every day and wouldn’t go back. But I’ve noticed a shift in how my recent teams work, and I wonder how much of it is down to AI.
      Are we becoming more productive as individuals at the expense of collaboration?
      Fewer whiteboards, thinner reviews
      Working through a hard problem used to mean getting a few developers around a whiteboard. Someone suggested an approach, someone disagreed, someone spotted what everyone had missed. You might spend an hour on something that took 20 minutes to build, but everyone understood how you got there.
      Now it’s tempting to open Claude, describe the problem and solve it alone. It’s quick and often excellent. But nobody else was part of the process.
      Code reviews are going the same way. They used to be one of the best ways to understand how colleagues thought. Now AI can review the code, find the bugs and even make the fixes. The risk is AI writing the code, AI reviewing it and developers approving changes they haven’t fully understood.
      A review isn’t just about catching bugs. It’s about knowing what your colleagues are building and why.
      The questions we no longer ask
      “Have you worked with this library before?” “Why was this service built this way?” “Can you have a quick look at something?”
      Those questions often went well beyond the original problem. You learned why decisions were made and picked up techniques from people with more experience. Now we ask AI instead.
      Not every question needs a colleague. But some of those interruptions were how knowledge spread around a team. That matters most for junior developers. AI is an incredible learning tool, but learning from a senior developer means watching how they think, not just getting the right answer. And some knowledge isn’t in the docs or the code. It lives with the people who built the system.
      Are we still working as teams?
      Imagine five developers on the same application. Each picks up a ticket, works through it with Claude, gets an AI review and moves on. Tickets move. Features ship.
      But how much do they know about what each other is building? Could they maintain each other’s code? Or have we created five developers working independently with five AI assistants?
      Stand-ups and sprint planning coordinate the work. They don’t build a shared understanding of the system. And they don’t replace a colleague who knows the history, knows the business and might tell you that you shouldn’t be building the thing at all.
      Productivity numbers won’t show this. What happens when a senior developer leaves, or something breaks in production and the person who built it isn’t around? You can’t measure shared knowledge and trust by counting merged pull requests.
      So, what’s the answer?
      Not to stop using AI. It has removed a lot of tedious work, and not every question needs a team discussion. But we should be more deliberate about the conversations we keep.
      • Use AI to explore an architecture, then talk it through with your colleagues.
      • Let AI review pull requests, but keep reviewing each other’s work.
      • Encourage juniors to use AI, but don’t let it replace mentorship.
      • When you solve something interesting, share what you learned.
      The goal isn’t more code. It’s better software built by better teams.
      AI is making us better at working independently. Whether it’s making us better engineering teams is another question entirely.
      3 February 2026
      Modernising without starting again
      Sometimes the difficult engineering decision is to keep what already works.
      When you spend time in mature software systems, you learn that rewriting everything is rarely the only option, and often isn’t the best one.
      Upgrading older PHP and MySQL applications isn’t just changing version numbers. Existing code may depend on behaviours that newer runtimes and databases no longer tolerate.
      The hidden contracts
      A warning that used to go unnoticed can become a production issue. A query that happened to return the desired result can fail under stricter grouping rules. Previously accepted dates can become invalid. Those assumptions need to be understood before architecture changes are made.
      Controlled change beats a heroic rewrite
      My preference is to establish a reliable test baseline, improve observability and make changes incrementally. Some problems need targeted compatibility fixes. Others deserve redesign. Those shouldn’t be confused.
      In practice, on a recent PHP 7.4 to 8.2 and MySQL 5 to 8 upgrade, that meant writing regression tests around the behaviour people relied on before touching the runtime, then fixing compatibility issues one application at a time. The tests made each release boring, which is exactly what you want from a migration.
      On another platform, incremental replacement using the Strangler Pattern allowed parts of an older system to evolve without shutting down the business workflows that depended on it.
      Keep the business in the conversation
      A cleaner architecture is valuable when it improves reliability, maintainability or delivery. A rewrite that delays useful work needs a stronger reason than ‘this would be nicer to build’.
      The aim isn’t to make every system new. It’s to make the systems people depend on safer to change.
